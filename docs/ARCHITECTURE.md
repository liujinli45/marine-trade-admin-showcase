# 架构说明

## 1. 部署形态

同一域名下暴露三件事：前端静态资源、业务 API、受控附件。

```
         ┌──────────────────────────────────────────────┐
浏览器 ──►│  网关：静态托管 · 反向代理 · 健康探针         │
         └───────┬───────────────────┬──────────────────┘
                 │                   │
        /、/admin/trade/         /api/*  /uploads/*
                 │                   │
                 ▼                   ▼
        前端 SPA（Vue 3）    业务 API（Express）
                                     │
                                     ▼
                              MySQL（连接池）
```

网关同时提供两个探针：

- `/health/live`：进程是否活着（容器健康检查用）；
- `/health/ready`：依赖是否就绪（数据库连通、备份新鲜度、磁盘余量等），
  未就绪返回 503 —— **容器 healthy 不等于服务 ready**，两者分开才能避免「容器在跑但接口全挂」。

## 2. 后端分层

```
app.js                  装配层：中间件顺序、路由挂载、错误兜底
routes/*.js             HTTP 编排：参数校验 → 事务边界 → 响应组装
middleware/*.js         横切关注点：认证、模块权限、资源访问
utils/*.js              业务规则（纯函数为主）、SQL 片段构造、导出
db.js / config.js       连接池与环境配置
migrations/*.js         顺序编号的数据库迁移
```

**关键约束：路由层不写业务规则。** 金额校验、团队范围、分页归一化、幂等回执都在 `utils/`，
好处是这些规则可以被单元测试直接覆盖，不需要起数据库或 HTTP 服务；
带数据库行为的编排则由集成测试覆盖。

### 2.1 装配层要点（`samples/api/app.js`）

- `helmet` 安全响应头、CORS 白名单（拒绝时返回业务错误码而不是抛裸异常）；
- 请求体上限 1 MB，超限转成 `REQUEST_TOO_LARGE`；
- **认证只挂载一次**：`app.use('/api', authMiddleware, ...)`
  —— 避免每个子路由重复校验 JWT 与重复查库；
- 每个业务模块挂载时附带模块权限中间件，权限声明与路由注册在同一处，便于审计；
- `/api` 未匹配路径返回 **JSON 404** 而不是 Express 默认的 HTML 404：
  前端拦截器按 JSON 读 `message`，拿到 HTML 会把整段标签当错误信息渲染；
- 全局错误处理把 `entity.too.large` / `LIMIT_FILE_SIZE` / CORS 拒绝统一映射为稳定错误码；
- 优雅退出：`SIGTERM/SIGINT` → 停定时任务 → 关 HTTP → 关连接池，
  超时兜底强制退出；`uncaughtException` / `unhandledRejection` 留下结构化日志再退出。

### 2.2 中间件顺序（有语义，不要随意调整）

```
requestContext（请求 ID / 慢请求日志）
  → helmet → CORS → JSON 解析（限 1MB）
  → /health
  → /uploads（公开附件，按数据库引用校验）
  → /api/auth（公开登录）
  → /api（限流 → 认证 → 强制改密）→ 各业务模块（模块权限）
  → /api 404 → 全局错误处理
```

## 3. 权限模型

四层收敛，逐层缩小到「数据行」：

| 层 | 位置 | 作用 |
| --- | --- | --- |
| 1. 会话 | `middleware/auth.js` | 校验 JWT + 回库比对 `token_version`，改密/下线即刻失效 |
| 2. 状态 | `requirePasswordChanged` | 未完成首次改密的账号只能改密 |
| 3. 功能 | `requireModulePermission` | 按模块拒绝，如无 `orders` 权限不能访问订单接口 |
| 4. 数据 | `utils/owner-scope.js` | 把可见范围编译进 SQL：经理可见本人 + 直属销售，销售只见本人 |

- 角色：`admin` / `manager` / `sales`；
- 经理的团队名单**每次请求从数据库读取**，不信任令牌里的旧声明，也不接受请求体传入；
- `ownerScopeSql` 对列名做白名单正则校验后才拼接，杜绝把用户输入变成 SQL 标识符；
- 列表、详情、导出、统计复用同一组范围函数 —— 权限差异只允许出现在一处。

前端另有一层路由守卫（`samples/web/router/guard.js`）负责体验：未登录跳登录页、
无菜单权限提示并回到首页。**它只是 UX，不是安全边界**——真正的拦截在后端。

## 4. 错误契约

```json
{ "code": 400, "message": "DEPOSIT_EXCEEDS_TOTAL" }
```

- `code` 为 HTTP 状态码语义，`message` 为**稳定的大写错误码**（或上游透传的码）；
- 前端按错误码映射到本地化文案，后端不负责措辞；
- 允许的例外：三元状态码（如改密必需）与上游透传，均需显式约定。

## 5. 数据访问

- `mysql2` 连接池；需要事务时显式 `getConnection()` → `beginTransaction()`；
- 事务入口的固定写法：**获取连接也在 try 内**，回滚失败不掩盖原始错误，
  连接在 `finally` 释放（连接池耗尽时的失败路径最容易在这里出问题）；
- 金额列使用定点小数存储，应用层按整数分计算，避免浮点误差；
- 分页统一走 `pagination()`：默认 20 条、上限 100 条、非法输入回退默认值、
  offset 溢出回到第一页 —— 参数直接进 `LIMIT/OFFSET` 是历史缺陷来源。

## 6. 与官网的边界

同一系统还包含对外官网（本仓库不含其代码）。两者通过一个**内网集成接口**联通：
官网提交的询盘经服务到服务的共享密钥校验后转为客户档案，且以 `source_inquiry_id` 做幂等，
重复调用返回同一条记录。

# 多语言与错误契约

界面支持中文 / 英文 / 俄文三种语言，且**后端不参与措辞**。

## 1. 为什么不让后端返回句子

早期做法是后端直接返回英文句子，前端原样展示。问题有三：

1. 文案改动等于接口变更，客户端版本滞后时会出现新旧混杂；
2. 无法用门禁约束 —— 句子是自由的，漏译与措辞漂移都不好查；
3. 同一错误在不同接口的措辞会自然发散。

现在的契约：

```json
{ "code": 400, "message": "DEPOSIT_EXCEEDS_TOTAL" }
```

- `message` 只允许**稳定的大写错误码**（snake_case 的码也在收口）；
- 前端按错误码查本地化文案，三语共用一个键，缺键在门禁阶段就会失败；
- 例外的形态只有两种：三元状态码（同一错误在不同状态下的码）与上游透传（保留其 `code`/`message`）。

## 2. 文案组织

前端按业务域拆分文案文件（客户、订单、报价、成本、权限、通知、统计……），
每种语言一个主文件，域文件在对应语言下展开。好处是：

- 改动集中在单个业务域，冲突面小；
- 新增语言只需补一份语言文件，不需要动业务代码；
- 术语可以集中校对（如报价单在俄语中用业务惯用的 КП）。

## 3. 三道门禁

多语言最大的风险不是「漏翻译」，而是**漏了却没人发现**。所以门禁分三层：

| 门禁 | 覆盖 | 说明 |
| --- | --- | --- |
| 硬编码中文扫描 | 中文字面量 | 扫源码中的中文文案，区分「漏译」与「有意保留」 |
| 英文散文全量普查 | 英文响应 | 只扫中文的扫描器对英文是盲区：任何含空格且含小写字母的响应串都算散文，必须改为错误码 |
| 严格三语检查 | 三语键位 | 三种语言的键必须对齐，缺键或空值直接失败 |

**英文全量普查是文件系统驱动的**：新增的源文件自动纳入范围，不需要手工登记 ——
否则「新文件没进清单」会成为永久漏洞。

## 4. 有意不统一的清单

术语表里保留了一份「有意不统一清单」：某些概念在不同语境下**故意**使用不同译法
（例如面向客户的单证用语与内部管理用语）。清单之外才要求统一，
避免后来者「顺手统一」反而改坏了业务惯用表达。

## 5. 与权限的结合

账号可设置**工作语言**。同一份数据在不同用户界面下按各自语言渲染，
但错误码、状态机取值与数据库存储值始终是语言无关的 —— 翻译只发生在展示层。

# 可靠性与一致性设计

财务类系统最容易出的不是「功能没做完」，而是**重试把数据写重了、并发把修改盖掉了、
失败路径留下了半截状态**。下面这些是专门为此做的设计。

## 1. 幂等：从按键到回执

### 后端

涉及金额写入的接口（订单、订单成本、订单变更、工厂付款、报价与其新版本）
**必须携带 `Idempotency-Key`**，缺失直接返回 `SUBMISSION_KEY_REQUIRED`。
键的格式由契约固定（长度与字符集受限），避免把任意字符串塞进唯一索引。

关键点：幂等键与业务结果**在同一事务里**写入回执表。
重试请求不是返回「重复提交」，而是返回**首次那次请求的真实结果**。
这样「提交成功但响应丢失」的场景才真正闭合。

### 前端

前端不生成随机键了事，而是按 **身份 + 请求路径 + 载荷** 计算 SHA-256 作为提交签名：

- 同一份内容重试（网络抖动、用户重复点击）→ 复用同一个键；
- 提交成功后**主动轮换**，让「用户确实要再录一笔」能得到新键；
- 签名与键同时写 `sessionStorage`，刷新页面后仍能续上未决的提交；
- 存储不可用时降级为内存 Map，保护不丢（`samples/web/api/submission-keys.js`）。

## 2. 并发：版本号 + 行锁

- 报价修改走**版本号**：请求必须带 `base_version_no`，在报价行锁内比较，
  不匹配返回冲突并**保留用户当前表单**，不静默覆盖；
- 所有状态变更操作都校验版本号；
- 订单变更申请保存**申请时的原值**，审批时在行锁内与当前值比对：
  期间订单已被他人修改则拒绝（`CHANGE_REQUEST_CONFLICT`），提示退回重提；
  历史数据缺可靠原值的申请**不自动放行**。

## 3. 事务边界

统一写法（历史上踩过的坑都在这里）：

```js
const connection = await pool.getConnection()   // 获取连接也在 try 内
try {
  await connection.beginTransaction()
  // ... 业务写入，同一连接
  await connection.commit()
} catch (error) {
  await connection.rollback().catch(() => {})   // 回滚失败不掩盖原始错误
  throw error
} finally {
  connection.release()                          // 一定释放，避免连接池耗尽
}
```

要点：

- **获取连接失败**（连接池耗尽）不能变成未处理的 Promise 拒绝；
- **回滚失败**不能顶掉真正的业务错误；
- 多步操作必须原子：例如「删除用户前先清空下属的经理字段」如果分成两个独立操作，
  删除失败时团队归属已经丢了 —— 现在两步同事务，失败全回滚。

## 4. 金额：拒绝非法输入，不静默修正

- 前端预览与后端计算复用**同一套纯函数**（报价合计、附加金额），消除「预览与实际不一致」；
- 金额按**整数分**计算，税额与合计最后统一舍入；
- 非法输入（非数字、负数、超额折扣、税率 > 100%、超出存储范围）一律返回受控的 400 与三语错误码
  —— 不静默归零、不截断、不丢弃无效明细行；
- 校验失败时前端**隐藏合计并禁用保存/PDF/打印**，保留输入便于修正，而不是提交一份错的数据。

## 5. 财务锁

订单一旦进入已确认/已完结状态，金额相关字段的修改被显式拒绝：

- 已确认定金后，定金金额不可改；
- 已收尾款或订单已完结，订单总额不可改；
- 已完结订单的价格与成本类字段整体锁定，需要改动走**订单变更申请**流程；
- 销售额角色在非可编辑状态下修改价格/成本类字段，被要求走审批而不是直接写入。

`utils/receipts.js` 里还有一条容易忽略的规则：订单上的「已收定金/已收尾款」标记与
「收付款记录」描述的是**同一笔钱**，两者取最大值而不是相加 —— 否则会双重计数。

## 6. 可观测性

- 每个请求带 `requestId`，日志为结构化 JSON（含 service、耗时、慢请求标记）；
- 进程级 `uncaughtException` / `unhandledRejection` 留下结构化记录后再退出，
  不留「没有服务名和请求 ID 的裸堆栈」；
- 健康探针区分 liveness 与 readiness（见 `docs/ARCHITECTURE.md`）。

## 7. 备份与恢复

- 每日自动备份数据库与上传附件，写状态文件，外部副本逐文件校验哈希；
- 恢复不是「脚本存在就算」，而是**定期做隔离恢复演练**：在临时容器里真实恢复，
  核对表数量与附件数量后销毁，不污染业务库；
- 备份新鲜度、异地副本时间纳入健康检查与提醒。
